# Cloudflare WARP Trades WireGuard Tags for MASQUE Streams

Cloudflare WARP has two data planes behind one undocumented REST API. A client first mints a device identity with an unauthenticated `POST https://api.cloudflareclient.com/<ver>/reg`. The response holds a device `id`, a bearer `token` that is never shown again, the inner addresses, the edge's public key and a 3-byte `client_id`. From there, traffic goes over one of two transports. The first is near-stock WireGuard on UDP 2408 and fallback ports, with the `client_id` written into the three "reserved" header bytes of every packet. The second is MASQUE: the client authenticates with mutual TLS on an enrolled ECDSA P-256 key and speaks a Cloudflare dialect of CONNECT-IP (`:protocol cf-connect-ip`) over HTTP/3 on UDP 443, with an HTTP/2 fallback on TCP 443. MASQUE has been the consumer default since December 2024. Cloudflare's proxy mode, described in March 2026 and copied by usque and mihomo within months, opens **one plain HTTP/3 `CONNECT host:port` stream per TCP flow**. That design removes the userspace TCP/IP stack that every older SOCKS/HTTP front-end needed (wireproxy, warp-plus, sing-box, Xray). For WarpClient this settles the design. `ITcpConnector.ConnectAsync(DnsEndPoint)` maps one-to-one onto an L4 stream, and .NET 10 already has nearly everything it needs: System.Net.Quic streams with client certificates, ECDSA P-256 and X.509. The one gap is a small hand-written HTTP/3/QPACK layer. The WireGuard and L3 MASQUE paths would instead need X25519 and BLAKE2s from NuGet, QUIC datagrams that .NET will not expose before .NET 12, and a managed TCP/IP stack that does not exist. Everything below comes from community reverse engineering, not a Cloudflare specification. The live risks are TLS-fingerprint-based 429s on registration, an undocumented requirement for 20-byte QUIC connection IDs, and Cloudflare's planned post-quantum-only phase.

## One unauthenticated POST mints a long-lived device identity

Every community client starts at the same reverse-engineered API, `https://api.cloudflareclient.com/<ver>/`, where `<ver>` is an Android app build string. The newest constants come from wgcf. Since September 2026 it sends `v0a5641` with `User-Agent: 1.1.1.1/6.38.9-5641 (Android 16.0.0)` and `CF-Client-Version: a-6.38.9-5641` ([wgcf api.go](https://github.com/ViRb3/wgcf/blob/de6bba7147dc965a1b8e4de113a709750697ccea/cloudflare/api.go)). The server does not appear to check that string. Repos in active use send anything from `v0a1922` to `v0a5641`, and warp-plus even pairs a `v0a4005` path with an `a-6.30-3596` header, yet all reportedly register ([warp-plus api.go](https://github.com/bepass-org/warp-plus/blob/f70ea7e4f193717c73f9a4357cbc98d6944b36bb/warp/api.go); [wgcf-cli request.go](https://github.com/ArchiveNetwork/wgcf-cli/blob/1b43d47c348a003949e064786378c643872d9db1/utils/request.go)). Zero Trust and Mesh registrations have moved to a second host, `api.devices.cloudflare.com`. It serves `POST /v0/reg` and `/v1/accounts/{account_tag}/reg/{id}`, as observed from the 2026.7 Linux `warp-svc` ([wgcf-mesh API.md](https://github.com/AnimMouse/wgcf-mesh/blob/8ddecda5690650798dba9c3c441aa8305223569a/API.md)).

Registration is a single unauthenticated `POST /<ver>/reg`. Only two fields carry weight: `key`, a base64 32-byte Curve25519 public key, and a `tos` timestamp. wgcf adds `key_type: "curve25519"`, `tunnel_type: "wireguard"`, `locale`, `model`, and empty `fcm_token`, `install_id` and `serial_number` ([wgcf api.go](https://github.com/ViRb3/wgcf/blob/de6bba7147dc965a1b8e4de113a709750697ccea/cloudflare/api.go)). warp-reg.sh sends nothing but `{"key","tos"}` ([warp-reg.sh](https://github.com/chise0713/warp-reg.sh/blob/8c93845d27a568992c9c62ae6d86a33d568d6050/warp-reg.sh)).

The response carries the device's entire credential set. It holds the `id`, a bearer `token` that is **returned only on this call**, an `account` object, and a `config` object. The `config` object contains `client_id`, `interface.addresses.{v4,v6}` and `peers[0].{public_key, endpoint.{host,v4,v6,ports}}`, with `ports` defaulting to `[2408, 500, 1701, 4500]` ([wgcf openapi-spec.yml](https://github.com/ViRb3/wgcf/blob/de6bba7147dc965a1b8e4de113a709750697ccea/openapi-spec.yml)). Endpoint addresses arrive with a dummy port, as in `162.159.193.5:0` or `[2606:4700:100::a29f:c105]:0`. Clients strip it and substitute a value from `ports` ([wgcf-mesh API.md](https://github.com/AnimMouse/wgcf-mesh/blob/8ddecda5690650798dba9c3c441aa8305223569a/API.md); [usque register.go](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/cmd/register.go)).

Every later call sends `Authorization: Bearer <token>` against `/reg/{id}`. `GET` re-fetches config, `PATCH` changes the key or name, `DELETE` removes the device, and `/reg/{id}/account…` manages licenses and bound devices ([wgcf openapi-spec.yml](https://github.com/ViRb3/wgcf/blob/de6bba7147dc965a1b8e4de113a709750697ccea/openapi-spec.yml)). No repo implements a token refresh, so clients keep `{id, token, private key, license}` indefinitely. Errors come back as `{"success": false, "errors": [{"code", "message"}]}`, with codes such as 1001 (invalid public key) and 2016 (unauthorized) ([usque apierror.go](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/models/apierror.go)).

Switching to MASQUE takes one more call. When the user picks MASQUE, the official Android app sends `PATCH /reg/{id}` with `{"key": <base64 SubjectPublicKeyInfo DER of a P-256 key>, "key_type": "secp256r1", "tunnel_type": "masque"}` ([usque RESEARCH.md](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/RESEARCH.md)). usque does this in two steps. It registers with a random 32-byte throwaway "key", then PATCHes the real P-256 key. In the response, `peers[0].public_key` becomes the edge's P-256 key in PEM, which the client pins ([usque cloudflare.go](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/api/cloudflare.go)). A 2026 registrar warns that some responses return that key as bare base64 DER instead ([warp-reg-gw registration.go](https://github.com/6Kmfi6HP/warp-reg-gw/blob/1c2edaefbf1233e8811b933c9a29298600093806/internal/registration/registration.go)). The evidence points to one key and one tunnel type per registration at a time. No repo has tested registering directly with a P-256 key.

In 2026 the hard part is the TLS handshake, not the JSON. In July, wgcf v2.2.31 fell from **roughly 90% to 10% registration success, failing with HTTP 429**, after a Go toolchain upgrade changed its ClientHello. Restoring the old fingerprint fixed it. It broke again in September, and v2.3.0 fixed it by pinning a uTLS hello that imitates Android Conscrypt ([wgcf #613](https://github.com/ViRb3/wgcf/issues/613); [wgcf #626](https://github.com/ViRb3/wgcf/issues/626)). That hello is TLS 1.2-only with exactly two cipher suites, ECDHE-ECDSA and ECDHE-RSA with AES-256-GCM-SHA384. Its extension order is fixed and ends in BoringSSL-style padding, it sends ALPN `http/1.1`, and its session ID is empty. wgcf also disables HTTP/2 and deletes the `Accept` header to match OkHttp ([wgcf api.go](https://github.com/ViRb3/wgcf/blob/de6bba7147dc965a1b8e4de113a709750697ccea/cloudflare/api.go)). Before 2025, forcing TLS 1.2 was enough to avoid `403` error 1020 ([wgcf api.go@8666a8be](https://github.com/ViRb3/wgcf/blob/8666a8be/cloudflare/api.go)).

Fingerprint enforcement looks specific to the consumer path. In October 2026, wgcf-mesh registered against `api.devices.cloudflare.com` with plain curl ([wgcf-mesh HANDOFF.md](https://github.com/AnimMouse/wgcf-mesh/blob/8ddecda5690650798dba9c3c441aa8305223569a/HANDOFF.md)). The API also publishes AAAA records, so registration fails on hosts that have an IPv6 address but no IPv6 route ([usque #127](https://github.com/Diniboy1123/usque/issues/127)).

**What it means for WarpClient.** Registration is where .NET is structurally weakest. `SslStream` delegates ClientHello construction to SChannel, OpenSSL or Apple's stack. WarpClient can still reproduce the recipe that used to beat error 1020: TLS 1.2 only, HTTP/1.1, wgcf's exact header set, and on Linux a two-suite `CipherSuitesPolicy`. It cannot reproduce the extension order and padding wgcf now needs to avoid 429s.

Registration should therefore be a rare, cached operation. WarpClient should persist `{id, token, private keys, client_id, license}`, back off exponentially on 429, and prefer IPv4 through a `SocketsHttpHandler.ConnectCallback`. It should also accept credentials imported from wgcf or usque, so a user is never blocked by the fingerprint. Deserialization must be lenient: wgcf broke three times in one year when fields it treated as required (`model`, `usage`, `key_type`) stopped arriving ([wgcf #629](https://github.com/ViRb3/wgcf/issues/629)). The peer key parser should accept PEM or DER.

## WARP's WireGuard is stock Noise plus a three-byte routing tag

On the wire, WARP's WireGuard is ordinary WireGuard. It uses Noise_IKpsk2 with the standard prologue, a 148-byte initiation, a 92-byte response and an all-zero pre-shared key. warp-plus's endpoint prober builds a plain initiation with `flynn/noise` and gets valid replies, and CloudflareWarpSpeedTest uses stock wireguard-go message builders ([warp-plus ping/warp.go](https://github.com/bepass-org/warp-plus/blob/f70ea7e4f1/ipscanner/ping/warp.go); [CloudflareWarpSpeedTest warping.go](https://github.com/puzige/CloudflareWarpSpeedTest/blob/4d00b536b9/task/warping.go)). Cloudflare's one extension is in header bytes 1–3, which the WireGuard spec reserves as zero. WARP uses them as a **per-registration routing tag equal to the base64-decoded `config.client_id`**. For example, `I0q+` decodes to `[35, 74, 190]` ([Xray-docs warp.md](https://github.com/XTLS/Xray-docs-next/blob/59ab79c7e09112475e7907bf745913ded7ca89a5/docs/en/document/level-2/warp.md); [warp-reg.sh](https://github.com/chise0713/warp-reg.sh/blob/8c93845d27a568992c9c62ae6d86a33d568d6050/warp-reg.sh)). Wireshark's dissector now recognises "Cloudflare Warp traffic which may use non-zero bytes for load balancing purposes" ([Wireshark commit](https://gitea.osmocom.org/osmith/wireshark/commit/69201185adfc0359abe08f6ed6befbea93c63f94)).

Black-box tests in Xray-core issue #1730 (March 2023) set the rules every working client still follows. The client writes the tag **after** computing MAC1 and MAC2 over a zero header; tagging before the MAC gets no reply. It must also zero bytes 1–3 of every received datagram before parsing, because the server tags its replies too ([Xray-core #1730](https://github.com/XTLS/Xray-core/issues/1730); [Xray commit 4c8ee0a](https://github.com/XTLS/Xray-core/commit/4c8ee0af50)).

A zero tag still gets a handshake, but a wrong non-zero tag gets no reply at all. At the Hong Kong and Los Angeles PoPs, data did not flow without the correct tag; Singapore worked without one. Transport-data packets are sealed with no additional authenticated data, so the tag on type-4 packets is unauthenticated routing metadata. The tag also belongs to the registration rather than the machine. A key and tag registered in Tokyo worked from a Hong Kong VPS, but one registration's tag paired with another registration's key did not ([Xray-core #1730](https://github.com/XTLS/Xray-core/issues/1730)).

| Client | Tag configuration | Write and strip rule |
|---|---|---|
| warp-plus (wireguard-go fork) | manual `reserved=a,b,c` or `random` | writes on message types 1–4 only, skipping junk packets; strips every received datagram |
| sing-box | `peers[].reserved` | writes every datagram over 3 bytes, with per-endpoint overrides; strips on receive |
| Xray-core | `reserved: [a,b,c]` | writes every datagram over 3 bytes; strips on receive |
| Aether (Rust, boringtun 0.7) | `client_id: [u8;3]` | injects and strips on types 1–4 at the UDP layer |
| wireproxy, wg-quick, upstream boringtun | none | zero tag only; fails where the tag is required |

Sources: [warp-plus peer.go](https://github.com/bepass-org/warp-plus/blob/f70ea7e4f1/wireguard/device/peer.go), [sing-box client_bind.go](https://github.com/SagerNet/sing-box/blob/testing/transport/wireguard/client_bind.go), [Xray bind.go](https://github.com/XTLS/Xray-core/blob/main/proxy/wireguard/bind.go), [Aether wireguard.rs](https://github.com/CluvexStudio/Aether/blob/a463ab71b5/aether/src/wireguard.rs), [wireproxy #72](https://github.com/windtf/wireproxy/issues/72), [boringtun noise/mod.rs](https://github.com/cloudflare/boringtun/blob/6dcc889a95/boringtun/src/noise/mod.rs).

Cloudflare's own boringtun has no tag hook upstream, although its README says it ships in the 1.1.1.1 apps ([boringtun README](https://github.com/cloudflare/boringtun/blob/6dcc889a95/README.md)). The official apps therefore presumably add the tag in code that has not been published.

Consumer WARP uses one static server key, `bmXOC+F1FxEMF9dyiK2H5/1SUtzH0JuVo51h2wPfgyo=`, which the API returns in `peers[0].public_key` ([CloudflareWarpSpeedTest warping.go](https://github.com/puzige/CloudflareWarpSpeedTest/blob/4d00b536b9/task/warping.go)). The endpoint host `engage.cloudflareclient.com` maps to `162.159.192.1` and `2606:4700:d0::a29f:c001`. The IPv6 address embeds the IPv4 address in its low 32 bits ([v2rayN Global.cs](https://github.com/2dust/v2rayN/blob/master/v2rayN/ServiceLib/Global.cs)).

Cloudflare documents **UDP 2408 as the default port with 500, 1701 and 4500 as fallbacks**. It lists 162.159.193.0/24 and 2606:4700:100::/48 as the Zero Trust WireGuard ranges, and notes that 162.159.192.0/24 serves consumer WARP ([Cloudflare One firewall docs](https://developers.cloudflare.com/cloudflare-one/connections/connect-devices/warp/deployment/firewall/)). Community scanners probe far more: an identical, undocumented list of 54 UDP ports across 162.159.192.0/24, 162.159.195.0/24, 188.114.96–99.0/24, 2606:4700:d0::/64 and 2606:4700:d1::/64. warp-plus dropped 162.159.193.0/24 in February 2025 ([warp-plus endpoint.go](https://github.com/bepass-org/warp-plus/blob/f70ea7e4f1/warp/endpoint.go)). The 2026 Rust core Aether still scans it and moves 2408, 500, 1701 and 4500 to the front of its sweep ([Aether wireguard.rs](https://github.com/CluvexStudio/Aether/blob/a463ab71b5/aether/src/wireguard.rs)).

A registration provides a /32 IPv4 address, commonly `172.16.0.2`, and a /128 inside `2606:4700:110::/48`, with AllowedIPs `0.0.0.0/0, ::/0` and DNS 1.1.1.1 ([wgcf profile.go](https://github.com/ViRb3/wgcf/blob/833a541b9a/wireguard/profile.go)). Clients disagree on MTU:

| Client | MTU | Source |
|---|---|---|
| wgcf | 1280, measured from the Android app's tun0 | [wgcf #40](https://github.com/ViRb3/wgcf/issues/40) |
| warp-plus | 1330 single, 1280 nested | [warp-plus app.go](https://github.com/bepass-org/warp-plus/blob/f70ea7e4f1/app/app.go) |
| sing-box | 1408 | [sing-box endpoint docs](https://github.com/SagerNet/sing-box/blob/testing/docs/configuration/endpoint/wireguard.md) |
| Xray and wireproxy | 1420 | [Xray conf](https://github.com/XTLS/Xray-core/blob/main/infra/conf/wireguard.go); [wireproxy config.go](https://github.com/windtf/wireproxy/blob/35cce290db/config.go#L620-L640) |

The wgcf issue documents the failure mode: without an explicit MTU, "ping&dns would usually work but https browsing never does". WireGuard adds 32 bytes of overhead on top of the UDP and IP headers. On a clean 1500-byte path that leaves 1440 bytes over IPv4 or 1420 over IPv6. Only 1280 survives PPPoE, mobile and nested paths.

Keepalives range from 5 s (warp-plus) to 25 s (Aether, and wgcf's opt-in flag). The keepalive matters because WARP sends no unsolicited traffic. An idle client behind NAT that sends nothing loses its inbound mapping.

Endpoint scanners time the gap from a handshake initiation to a valid response. CloudflareWarpSpeedTest sends ten initiations per IP:port and requires an exact 92-byte reply. In its default mode it replays one hard-coded initiation. That only makes sense if the edge does not enforce WireGuard's timestamp replay protection, which is an inference from the code, not a live test ([CloudflareWarpSpeedTest warping.go](https://github.com/puzige/CloudflareWarpSpeedTest/blob/4d00b536b9/task/warping.go)). Handshake-only probes overstate quality, because #1730 shows cases where the handshake succeeds and data does not flow. Aether therefore verifies the data plane with a DNS query through the tunnel, and warp-plus fetches `connectivity.cloudflareclient.com/cdn-cgi/trace` ([Aether wireguard.rs](https://github.com/CluvexStudio/Aether/blob/a463ab71b5/aether/src/wireguard.rs); [warp-plus wg.go](https://github.com/bepass-org/warp-plus/blob/f70ea7e4f1/app/wg.go)).

The fixed 148-byte handshake, sent to a few well-known /24s, is easy to fingerprint. Cloudflare itself acknowledges that some ISPs block WireGuard deliberately ([Cloudflare blog, 2024-03-06](https://blog.cloudflare.com/zero-trust-warp-with-a-masque/)), and Iran blocked WARP broadly in 2024 ([warp-plus #124](https://github.com/bepass-org/warp-plus/issues/124)). Community clients add junk traffic that the server silently drops. warp-plus sends 20–50 random or QUIC-shaped packets before every handshake and keepalive ([warp-plus send.go](https://github.com/bepass-org/warp-plus/blob/f70ea7e4f1/wireguard/device/send.go)). Others use AmneziaWG's client-only Jc and I1–I5 packets. AmneziaWG's header-changing features need server support, so they cannot be used against WARP ([amneziawg-go README](https://github.com/amnezia-vpn/amneziawg-go/blob/ce7cf1034d/README.md)).

**What it means for WarpClient.** A managed WireGuard data plane can be built, but every layer has a gap. The nearest starting point is Proxylity.WireGuardClient 0.2.0 (MIT, targets `net10.0`). It implements Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s, transport encryption and automatic rekeying in managed code on top of NSec and Blake2Fast, and it exchanges raw IP datagrams ([proxylity/wg-client](https://github.com/proxylity/wg-client)). WarpClient would have to wrap or fork it where datagrams are sent and received, following Aether's rule: stamp the tag after MACs, strip it before parsing, and touch only message types 1–4.

The BCL covers ChaCha20-Poly1305, with platform floors such as Android API 28. It lacks X25519 and BLAKE2s ([Microsoft Learn: cross-platform cryptography](https://learn.microsoft.com/en-us/dotnet/standard/security/cross-platform-cryptography)). `X25519DiffieHellman` is approved for .NET 11, with an out-of-band package under discussion ([dotnet/runtime #126206](https://github.com/dotnet/runtime/issues/126206)). The BLAKE2 request has been open since 2023 ([dotnet/runtime #80900](https://github.com/dotnet/runtime/issues/80900)).

Even with all of that in place, the output is still IP packets, so this path needs the TCP/IP stack discussed below. WarpClient should default to MTU 1280, always send the tag when `client_id` is known, and verify connectivity with the trace URL rather than the handshake alone.

## MASQUE replaces WireGuard keys with mTLS and a Cloudflare dialect of CONNECT-IP

| Date | MASQUE milestone | Source |
|---|---|---|
| 2024-03-06 | Announced for Zero Trust, to make WARP "look like HTTPS" and meet FIPS | [Cloudflare blog](https://blog.cloudflare.com/zero-trust-warp-with-a-masque/) |
| 2024-12-27 | Became the consumer default | [Cloudflare blog](https://blog.cloudflare.com/masque-now-powers-1-1-1-1-and-warp-apps-dex-available-with-remote-captures/) |
| May 2025 | HTTP/2 fallback in clients | [usque #32](https://github.com/Diniboy1123/usque/issues/32) |
| September 2025 | Post-quantum key agreement | [Cloudflare blog](https://blog.cloudflare.com/post-quantum-warp/) |
| March 2026 | L4 proxy mode described | [Cloudflare blog](https://blog.cloudflare.com/faster-sase-proxy-mode-quic/) |

The Zero Trust settings page now labels MASQUE "(default)" ([Cloudflare One WARP settings](https://developers.cloudflare.com/cloudflare-one/connections/connect-devices/warp/configure-warp/warp-settings/)). Cloudflare has published no wire specification. The open-source reference is Diniboy1123/usque (Go, v4.2.1, July 2026). mihomo (January 2026), yuhaiin and Xray-core (October 2026) all reuse its reverse-engineered constants ([usque README](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/README.md); [mihomo transport/masque](https://github.com/MetaCubeX/mihomo/tree/Alpha/transport/masque); [Xray-core PR #6878](https://github.com/XTLS/Xray-core/pull/6878)). The official client is written in Rust on quiche and BoringSSL ([usque RESEARCH.md](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/RESEARCH.md)).

### Identity lives in the TLS handshake, not the HTTP request

MASQUE authenticates entirely with mutual TLS 1.3. The client presents a self-signed X.509 certificate over its enrolled P-256 key. Dumps of the official client show it mints a new certificate for every connection, valid for 24 hours, and Cloudflare only checks that the certificate's public key is the one registered for the device ([usque RESEARCH.md](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/RESEARCH.md)). usque uses serial 0 and an empty subject; Xray uses a random serial and `NotBefore = now − 1h` ([usque utils.go](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/internal/utils.go); [Xray warp.go](https://github.com/XTLS/Xray-core/blob/main/transport/internet/masque/warp.go)). An unenrolled key, or a device with `warp_enabled` off, gets a TLS `access denied` alert ([usque masque.go](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/api/masque.go); [Xray-core PR #6878](https://github.com/XTLS/Xray-core/pull/6878)).

The client does not validate the server's hostname or chain. Instead it pins the edge's P-256 SubjectPublicKeyInfo from the registration response. For consumers that is `MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAEIaU7MToJm9NKp8YfGxR6r+/h4mcG7SxI8tsW8OR1A5tv/zCzVbCRRh2t87/kxnP6lAy0lkr7qYwu+ox+k3dr6w==` ([usque README](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/README.md#configuration)). FedRAMP and HTTP/2 endpoints can use different keys ([usque #81](https://github.com/Diniboy1123/usque/issues/81); [usque wiki: HTTP/2](https://github.com/Diniboy1123/usque/wiki/HTTP-2-support)).

The server accepts **only secp256r1 or the hybrid P256Kyber768Draft00** for key exchange. A client that leads with an X25519 key share gets a HelloRetryRequest, which costs one extra round trip ([usque #81](https://github.com/Diniboy1123/usque/issues/81)). Cloudflare's post-quantum post scheduled a PQC-only "Phase 2" for mid-2026 ([Cloudflare blog](https://blog.cloudflare.com/post-quantum-warp/)). The most recent evidence still shows classical P-256 working: Xray's Go client, which lacks the Kyber draft, connected in October 2026 ([Xray-core PR #6878](https://github.com/XTLS/Xray-core/pull/6878)).

### The L3 tunnel departs from the RFCs in five ways

The full-tunnel mode is HTTP/3 CONNECT-IP with Cloudflare's own values. The client connects with ALPN `h3` and SNI `consumer-masque.cloudflareclient.com` (`zt-masque.cloudflareclient.com` for Zero Trust). It then sends a single Extended CONNECT on stream 0, captured from the official client's qlog as `{":method":"CONNECT",":scheme":"https",":authority":"cloudflareaccess.com",":path":"/",":protocol":"cf-connect-ip","user-agent":"","capsule-protocol":"?1"}` ([usque RESEARCH.md](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/RESEARCH.md); [usque-app h3-connect.json](https://github.com/GeorgeXie2333/usque-app/blob/HEAD/oracle/fixtures/h3-connect.json)).

That request is the first departure. The standard `connect-ip` token returns HTTP 400, and RFC 9484's `/.well-known/masque/ip/…` URI templates are never used. Second, the server does not advertise `SETTINGS_ENABLE_CONNECT_PROTOCOL`. Third, it never sends ROUTE_ADVERTISEMENT or ADDRESS_ASSIGN capsules, so a client that waits for routes hangs forever. These three deviations are why usque had to fork quic-go/connect-ip-go, whose README says Cloudflare "isn't exactly RFC 9484 compliant" ([connect-ip-go fork client.go](https://github.com/Diniboy1123/connect-ip-go/blob/66cba32d7d33/client.go#L33)). Fourth, the server requires datagram support in the client's SETTINGS. Clients send both the RFC 9297 H3_DATAGRAM setting and the obsolete draft setting `0x276 = 1`, which the official client still emits ([usque masque.go](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/api/masque.go)). Fifth, at the QUIC layer the backend expects **20-byte client connection IDs**. Without them, usque measured 20–50% of 40 test connections failing with `PROTOCOL_VIOLATION`. The July 2026 fix set `ConnectionIDLength: 20` and added a single dial retry ([usque commit 6aa03fc](https://github.com/Diniboy1123/usque/commit/6aa03fc97d12848dce34eedbd187fb1077b5d1ea)).

After a 200 response, every IP packet travels as one QUIC DATAGRAM frame: the quarter-stream-ID varint, then context ID `0x00`, then the full IPv4 or IPv6 packet ([usque tunnel.go](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/api/tunnel.go)). The client takes its inner addresses (`172.16.0.2`, `2606:4700:110:…`) from the registration, because the server never assigns them in-band.

The inner MTU is fixed at 1280; usque warns that any other value is unsupported. Oversized packets get a locally generated ICMP Packet Too Big ([connect-ip-go fork conn.go](https://github.com/Diniboy1123/connect-ip-go/blob/66cba32d7d33/conn.go)). At roughly 41–46 bytes of encapsulation overhead, a 1280-byte inner packet needs about 1325 bytes of UDP payload. That fits the official client's **1350-byte initial packet size** but not quic-go's conservative 1252/1232-byte start. usque #123 shows the result: under the gVisor netstack, which ignores Packet Too Big, every TLS handshake stalled until the maintainer moved to 1350 ([usque #123](https://github.com/Diniboy1123/usque/issues/123)). Receive buffers must also exceed 1280, because yuhaiin found 1308–1328-byte inner packets arriving and a short buffer tearing the tunnel down ([yuhaiin masque.md](https://github.com/yuhaiin/yuhaiin/blob/HEAD/docs/masque.md)). The server closes connections after about five minutes of inactivity with `H3_NO_ERROR`, and the official client simply reconnects ([usque #30](https://github.com/Diniboy1123/usque/issues/30)).

### HTTP/2 fallback carries bare IP packets in capsules

When UDP is blocked, clients from May 2025 onward fall back to TCP 443 at `162.159.198.2`. A corporate network that blocked QUIC entirely showed `Tunnel Protocol: MASQUE (HTTP/2)` in August 2025 ([usque #32](https://github.com/Diniboy1123/usque/issues/32)). The wire format is a plain HTTP/2 `CONNECT` to `cloudflareaccess.com:443`. A `cf-connect-proto: cf-connect-ip` header carries the CONNECT-IP semantics, alongside `pq-enabled: false` and an empty user agent. The body is a stream of RFC 9297 capsules of type `0x00`, each holding a raw IP packet **without** the context ID RFC 9484 requires ([connect-ip-go fork client_h2.go](https://github.com/Diniboy1123/connect-ip-go/blob/66cba32d7d33/client_h2.go#L88); [usque-app h2-connect.json](https://github.com/GeorgeXie2333/usque-app/blob/HEAD/oracle/fixtures/h2-connect.json); [yuhaiin masque.md](https://github.com/yuhaiin/yuhaiin/blob/HEAD/docs/masque.md)). usque says the HTTP/2 endpoint "cannot be reliably pulled from the API" and hard-codes it ([usque wiki: HTTP/2](https://github.com/Diniboy1123/usque/wiki/HTTP-2-support)).

### L4 proxy mode turns each TCP flow into one HTTP/3 stream

In March 2026 Cloudflare described its new local proxy mode. SOCKS5 and HTTP proxy requests now ride as HTTP/3 `CONNECT` "encapsulated directly into a QUIC stream", which replaced a smoltcp userspace stack that Cloudflare called a performance ceiling. **Download and upload speeds doubled**, WireGuard was deprecated for proxy mode, and the feature needs client 2025.8.779.0 or later ([Cloudflare blog](https://blog.cloudflare.com/faster-sase-proxy-mode-quic/)).

usque v4.0.0 reproduced the mode in June 2026 using a distinct SNI, `consumer-masque-proxy.cloudflareclient.com`, and the same mTLS. All flows share one cached QUIC connection with 20-byte connection IDs and datagrams disabled. Each flow opens a request stream and sends a classic `CONNECT` with `:authority host:port` and no `:protocol`. Any 2xx response turns the stream into the TCP byte pipe. Unless local resolution is requested, the hostname itself goes to Cloudflare, and on a stale connection usque reconnects once and retries ([usque consts.go](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/internal/consts.go); [usque l4proxy.go](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/api/l4proxy.go)).

The limits are strict. L4 works over HTTP/3 only and carries no UDP, because "Cloudflare does not appear to support this on their end". Any other SNI is rejected with HTTP 403, and Zero Trust accounts reportedly need `zt-masque-proxy.cloudflareclient.com` ([usque wiki: L4 proxy mode](https://github.com/Diniboy1123/usque/wiki/L4-proxy-mode); [usque #126](https://github.com/Diniboy1123/usque/issues/126)). mihomo shipped the same mode one day after usque ([mihomo commit 8e2aba40fc](https://github.com/MetaCubeX/mihomo/commit/8e2aba40fc)).

| Mode | SNI (consumer) | ALPN | Request | Endpoint | Payload |
|---|---|---|---|---|---|
| L3, HTTP/3 | `consumer-masque.cloudflareclient.com` (any SNI works) | `h3` | Extended CONNECT, `:protocol cf-connect-ip`, `:authority cloudflareaccess.com`, `:path /` | 162.159.198.1 / 2606:4700:103::1, UDP 443 | QUIC DATAGRAM: quarter-stream-ID + context 0 + IP packet |
| L3, HTTP/2 | same (any SNI works) | `h2` | CONNECT `cloudflareaccess.com:443` + `cf-connect-proto: cf-connect-ip` | 162.159.198.2, TCP 443 | Capsule type 0x00 + length + IP packet, no context ID |
| L4, HTTP/3 | `consumer-masque-proxy.cloudflareclient.com` (exact match) | `h3` | Classic CONNECT `host:port`, one stream per flow | MASQUE edge, UDP 443 | Raw TCP bytes in HTTP/3 DATA frames |

Cloudflare documents only the Zero Trust MASQUE range: 162.159.197.0/24 and 2606:4700:102::/48, on UDP 443 with fallbacks 500, 1701, 4500, 4443, 8443 and 8095, plus TCP 443 ([Cloudflare One firewall docs](https://developers.cloudflare.com/cloudflare-one/connections/connect-devices/warp/deployment/firewall/)). The consumer 162.159.198.x addresses come only from reverse engineering.

Because the client pins the server key, the L3 tunnel accepts any SNI; in Xray's words, "the sni can be anything" ([Xray-core PR #6878](https://github.com/XTLS/Xray-core/pull/6878)). L4 mode gives up that freedom just as censors have learned to read QUIC SNIs. Initial packet keys derive from public values, and Russia's TSPU has moved to SNI-based QUIC filtering ([FOCI 2026](https://www.petsymposium.org/foci/2026/foci-2026-0010.php)). Russian users reported MASQUE "heavily blocked" by some ISPs from about February 2026. Their workarounds were QUIC fakes or the TCP fallback ([ntc.party thread](https://ntc.party/t/cloudflare-warp-%D0%BF%D0%B5%D1%80%D0%B2%D1%8B%D0%B9-%D1%81%D1%80%D0%B5%D0%B4%D0%B8-%D0%B2%D1%81%D0%B5%D1%85/15292?page=19)). During Iran's June 2025 blackout nearly all UDP was blocked ([Lantern corpus](https://corpus.lantern.io/techniques/http3-quic-block/)).

**What it means for WarpClient.** The three modes fit .NET very differently. L4 needs only QUIC bidirectional streams, client certificates and a plain CONNECT. System.Net.Quic has offered streams and `SslClientAuthenticationOptions` on msquic since .NET 9 ([Microsoft Learn: QUIC](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/quic/quic-overview)). The client side maps onto standard APIs: create the P-256 key with `ECDsa`, export its SubjectPublicKeyInfo for the PATCH, and mint the 24-hour certificate with `CertificateRequest.CreateSelfSigned`. Server pinning goes in `RemoteCertificateValidationCallback`, which compares the leaf's SubjectPublicKeyInfo bytes and ignores name and chain errors.

L3 over HTTP/3 does not fit, because it needs QUIC DATAGRAM frames, which .NET exposes no earlier than the 12.0.0 milestone ([dotnet/runtime #53533](https://github.com/dotnet/runtime/issues/53533)). The HTTP/2 fallback would need hand-written HTTP/2 framing over `SslStream`, because HttpClient cannot send a plain CONNECT over HTTP/2 ([dotnet/runtime #88003](https://github.com/dotnet/runtime/issues/88003)). HttpClient is no help over HTTP/3 either: `SocketsHttpHandler` never sends Extended CONNECT over HTTP/3 ([HttpConnectionPool.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Net.Http/src/System/Net/Http/SocketsHttpHandler/ConnectionPool/HttpConnectionPool.cs#L424-L428)).

The open question is whether System.Net.Quic can be made to use **20-byte connection IDs**; the research did not confirm it. L4 does not depend on the 1350-byte initial size, because QUIC segments stream data itself. The connection-ID requirement does apply to L4, and it fails intermittently, so any test needs dozens of connections, not one.

## WARP+ and Zero Trust change the account, not the wire

WARP+ is a license attached to the device, not a different protocol. `PUT /reg/{id}/account` with `{"license": "xxxxxxxx-xxxxxxxx-xxxxxxxx"}` moves the device under the license's account as a `child`. Per wgcf, an account holds at most **5 linked devices**, and exceeding that returns a generic 400 ([wgcf update.go](https://github.com/ViRb3/wgcf/blob/de6bba7147dc965a1b8e4de113a709750697ccea/cmd/update/update.go); [wgcf #76](https://github.com/ViRb3/wgcf/issues/76)). Cloudflare ended the referral program on 2024-11-01. That killed the key generators, which registered throwaway devices with `referrer` set ([WarpPlusKeyGenerator-NG #9](https://github.com/0x24a/WarpPlusKeyGenerator-NG/issues/9); [wgcf-cli cmd_plus.go](https://github.com/ArchiveNetwork/wgcf-cli/blob/1b43d47c348a003949e064786378c643872d9db1/cmd/wgcf-cli/cmd_plus.go)). wgcf's README now says only subscriptions bought in the official app work. It also documents a server-side bug: a device that has ever connected cannot gain WARP+ after binding, so the workaround is to register fresh and bind immediately ([wgcf README](https://github.com/ViRb3/wgcf/blob/de6bba7147dc965a1b8e4de113a709750697ccea/README.md)).

The transport does affect WARP+. Since early 2025, paying users see `warp=on` over WireGuard while the official MASQUE client reports `warp=plus`, and usque's author found the difference "doesn't seem to be cosmetic only" ([wgcf #459](https://github.com/ViRb3/wgcf/issues/459)). Community docs, marked as AI-written and labelled "tested", list separate MASQUE edges by account type, all with the same pinned key: 162.159.198.2 for free accounts, 162.159.199.2 for WARP+ and 162.159.197.2 for Zero Trust, with matching `2606:4700:103/104/102::2` addresses ([Xray-docs warp.md](https://github.com/XTLS/Xray-docs-next/blob/59ab79c7e09112475e7907bf745913ded7ca89a5/docs/en/document/level-2/warp.md)). One user's WARP+ login failure on 162.159.198.2 fits that split ([usque #134](https://github.com/Diniboy1123/usque/issues/134)).

Zero Trust adds one header to the same registration: `CF-Access-Jwt-Assertion: <JWT>`, where the JWT comes from `https://<team>.cloudflareaccess.com/warp` after browser SSO ([wgcf #56](https://github.com/ViRb3/wgcf/issues/56); [usque README](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/README.md)). wgcf-mesh verified a headless service-token flow in October 2026. A `GET` to that URL with `CF-Access-Client-Id` and `CF-Access-Client-Secret` answers with a `302` to `com.cloudflare.warp://<team>.cloudflareaccess.com/auth?token=<JWT>`. The JWT is RS256 and **valid for only 60 seconds**, so the client must immediately `POST /v0/reg` on `api.devices.cloudflare.com`. The response comes wrapped in `{"result": …, "success": true}`, with `account_type: "team"` and no license, and later calls go to `/v1/accounts/{account_id}/reg/{id}` ([wgcf-mesh API.md](https://github.com/AnimMouse/wgcf-mesh/blob/8ddecda5690650798dba9c3c441aa8305223569a/API.md)). The `policy` object in the response carries the device profile, including `tunnel_protocol`, `include`/`exclude` routes and `override_*_endpoint` ([wgcf openapi-spec.yml](https://github.com/ViRb3/wgcf/blob/de6bba7147dc965a1b8e4de113a709750697ccea/openapi-spec.yml)). Zero Trust uses its own SNIs (`zt-masque`, `zt-masque-proxy`) and ranges (162.159.193.0/24 for WireGuard, 162.159.197.0/24 for MASQUE). The older route is decaying. A usque `--jwt` registration on the consumer `/v0a…` path returned HTTP 500 in January 2026 ([usque #68](https://github.com/Diniboy1123/usque/issues/68)). An APKMirror release-note summary says the consumer 1.1.1.1 app drops Zero Trust login in May 2026 ([APKMirror, unverified](https://www.apkmirror.com/?p=13566116)), consistent with fscarmen removing Teams account types in January 2026 ([fscarmen/warp-sh](https://github.com/fscarmen/warp-sh/blob/78e86a8691a07523618167b3e9db8fabe6a0e8d6/README_EN.md)).

**What it means for WarpClient.** Account type (consumer, WARP+ or Zero Trust) belongs in configuration over a single transport implementation. It selects the API host and path family, the SNI pair and the endpoint set, and does not need a separate code path. Because the JWT lives only 60 seconds, the Zero Trust chain must run without user interaction. Set `AllowAutoRedirect = false`, since the `Location` header points at a custom URI scheme. `api.devices.cloudflare.com` accepted plain curl in wgcf-mesh's tests, so stock HttpClient registration should work there even where the consumer path rejects .NET's fingerprint. License binding should check the device count first. Health checks should read `warp=on` or `warp=plus` from `/cdn-cgi/trace` through the connector itself.

## Userspace clients borrow a netstack for TCP, until L4 mode removed it

Every pre-2026 WARP proxy has the same architecture. A local SOCKS5 or HTTP listener accepts a TCP connection and calls `DialContext(target)` on a userspace TCP/IP stack, almost always gVisor wrapped by wireguard-go's `tun/netstack`. That stack emits raw IP packets into a virtual TUN device. From there, a wireguard-go device encrypts them into UDP, or a CONNECT-IP client ships them as HTTP/3 datagrams, and the proxy splices the two byte streams ([wireproxy wireguard.go](https://github.com/windtf/wireproxy/blob/35cce290db/wireguard.go#L26-L83); [wireguard-go netstack](https://github.com/WireGuard/wireguard-go/blob/2631ce99a0/tun/netstack/tun.go#L55-L72)).

| Tool | Design | Behaviour that matters for WARP |
|---|---|---|
| wireproxy | Stock wireguard-go, gVisor netstack, go-socks5 | **No `reserved` setting** (open since 2023), so it fails wherever the tag is required. Uses the OS resolver unless `DNS =` is set. Returns one shuffled address with no IPv6 fallback ([wireproxy #72](https://github.com/windtf/wireproxy/issues/72); [wireproxy routine.go](https://github.com/windtf/wireproxy/blob/35cce290db/routine.go#L66-L121)) |
| warp-plus | Forked wireguard-go with `reserved` and junk "tricks" | Waits up to 15 s for a handshake and runs an HTTP connectivity test before exposing the proxy. Resolves hostnames inside the tunnel ([warp-plus wg.go](https://github.com/bepass-org/warp-plus/blob/f70ea7e4f1/app/wg.go); [warp-plus proxy.go](https://github.com/bepass-org/warp-plus/blob/f70ea7e4f1/wiresocks/proxy.go#L33-L118)) |
| usque full modes | Same gVisor netstack with no WireGuard device, pumping packets into CONNECT-IP | 833.60 Mbps down on a Ryzen 7 5700U at about 26% CPU ([usque README](https://github.com/Diniboy1123/usque/blob/6aa03fc97d12848dce34eedbd187fb1077b5d1ea/README.md)) |
| sing-box | WireGuard "endpoint" on sing-tun's gVisor stack | `DialContext` needs an IP address, so domains are resolved first ([sing-box device_stack.go](https://github.com/SagerNet/sing-box/blob/testing/transport/wireguard/device_stack.go#L51-L75)) |
| Xray-core | Own lightweight stack for WireGuard and MASQUE since 2026-10-15, replacing gVisor | 240 vs 143 MB/s single-stream; recovers from a 60 s outage in 0.6 s instead of 46 s ([Xray-core PR #7156](https://github.com/XTLS/Xray-core/pull/7156)) |

Xray's stack runs to about 1,900 lines. Its fixed 1 MiB window caps a single connection at 1.6 MB/s over a 100 ms RTT, against gVisor's 4.4 MB/s ([Xray-core #7130](https://github.com/XTLS/Xray-core/issues/7130)).

The same failures recur across these trackers. The most visible is MTU and PMTU black holes, worst where gVisor ignores ICMP Packet Too Big ([usque #123](https://github.com/Diniboy1123/usque/issues/123)). Single-connection throughput is poor: wireproxy users measured about 3.2 MB/s on one connection while parallel tests nearly saturated the link ([wireproxy #55](https://github.com/windtf/wireproxy/issues/55)). DNS leaks whenever resolution falls back to the OS, and none of these tools implements happy-eyeballs. SOCKS5 UDP is fragile. warp-plus pins each UDP association to its first destination ([warp-plus socks5 server.go](https://github.com/bepass-org/warp-plus/blob/f70ea7e4f1/proxy/pkg/socks5/server.go#L303-L349)). wireproxy's UDP relay listened on all interfaces until September 2026 ([wireproxy PR #224](https://github.com/windtf/wireproxy/pull/224)). usque's L4 modes avoid every stack-related item on that list by skipping "the extra user-space networking stack" altogether ([usque wiki: L4 proxy mode](https://github.com/Diniboy1123/usque/wiki/L4-proxy-mode)).

**What it means for WarpClient.** `ITcpConnector.ConnectAsync(DnsEndPoint)` sits exactly where these tools call `tnet.DialContext`, so the abstraction boundary is in the right place. Under the L3 paths, though, nothing managed exists to fill it. GitHub turns up only toy C# TCP/IP stacks, and the one C# tun2socks (VEthernet) P/Invokes native lwIP ([VEthernet](https://github.com/liulilittle/VEthernet)). The author of WireGuard.Net, a student prototype, tried a home-grown stack and dropped it as unstable ([Scartzz/WireGuard.Net](https://github.com/Scartzz/WireGuard.Net)). If L3 is ever needed, the realistic options are a port of a proven stack or a native binding. Xray's roughly 1,900 lines of Go are the most compact template that already handles Packet Too Big, fragments and timestamps. The alternative is binding native lwIP or smoltcp for each runtime identifier.

DNS policy follows from the mode. In L4, pass `DnsEndPoint.Host` straight to Cloudflare: no local query is made, so nothing leaks, and the edge picks the address family. In L3, resolve inside the tunnel and never fall back to the OS. A SOCKS5 front-end, if added, should be a hand-written RFC 1928 CONNECT subset, since no maintained C# SOCKS5 server library exists. It should bind to loopback with authentication on by default. usque's `0.0.0.0` with no authentication shows the cost of the opposite default.

## WarpClient should ship MASQUE L4 first behind ITcpConnector

| Need | Required by | .NET 10 status | WarpClient approach |
|---|---|---|---|
| ECDSA P-256 key, SubjectPublicKeyInfo export, self-signed X.509 | MASQUE enrollment and mTLS | In the BCL on all platforms ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/standard/security/cross-platform-cryptography)) | `ECDsa`, `CertificateRequest` |
| QUIC v1 bidirectional streams with client certificates | MASQUE L4 | `System.Net.Quic` on msquic; Linux needs `libmsquic`; macOS only partially supported ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/quic/quic-overview)) | Use directly; verify 20-byte connection IDs |
| HTTP/3 framing and QPACK for CONNECT | MASQUE L4 | HttpClient unusable for HTTP/3 CONNECT tunnels | Hand-write a control stream with SETTINGS, QPACK static table plus literals, HEADERS and DATA frames |
| QUIC DATAGRAM frames | MASQUE L3 over HTTP/3 | Not exposed; milestone .NET 12 ([#53533](https://github.com/dotnet/runtime/issues/53533)) | Defer, or P/Invoke msquic directly |
| Plain HTTP/2 CONNECT with capsules | MASQUE L3 over TCP | No plain CONNECT over HTTP/2 ([#88003](https://github.com/dotnet/runtime/issues/88003)) | Hand-write HTTP/2 over `SslStream` |
| X25519, BLAKE2s, XChaCha20 | WireGuard | ChaCha20-Poly1305 in the BCL; X25519 in .NET 11; BLAKE2 still requested | Proxylity.WireGuardClient on NSec and Blake2Fast |
| Userspace TCP/IP stack | Every L3 path | No usable managed stack | Port Xray's stack, or P/Invoke lwIP or smoltcp |
| Registration ClientHello shaping | Consumer `/reg` | Not customizable | Cache credentials, back off, import from wgcf or usque |

The first implementation should be a `MasqueL4Connector`. It holds one lazily created, shared `QuicConnection` to the MASQUE edge. That connection uses SNI `consumer-masque-proxy.cloudflareclient.com` (or the `zt-` variant for Zero Trust) and ALPN `h3`. It presents a client certificate minted from the enrolled key and rotated before its 24 hours lapse, and it trusts the server by SubjectPublicKeyInfo comparison. Once connected, it sends the HTTP/3 control stream with SETTINGS, mirroring usque's choices. Each `ConnectAsync` opens a bidirectional stream and writes a QPACK-encoded HEADERS frame carrying `:method CONNECT` and `:authority host:port`, with IPv6 literals in brackets. It requires a 2xx response. It then returns a `Stream` that wraps writes in DATA frames, unwraps DATA frames on read, and maps `CompleteWrites` to a FIN so TCP half-close survives. Failures should map to diagnoses:

| Failure | Meaning | Action |
|---|---|---|
| TLS `access denied` | Enrollment problem, or `warp_enabled` is off | Re-enroll or enable WARP on the device |
| HTTP 403 | Wrong SNI for the account type | Use the SNI that matches the account |
| `H3_NO_ERROR` | Idle reclaim by the server | Reconnect |
| `PROTOCOL_VIOLATION` | Connection-ID length | Retry once, as usque does |

The captured header fixtures in GeorgeXie2333/usque-app give byte-level oracles for unit tests ([usque-app fixtures](https://github.com/GeorgeXie2333/usque-app/blob/HEAD/oracle/fixtures/h3-connect.json)). Three spikes should come before anything else, in this order. The first is an msquic handshake with mTLS and pinning against the L4 edge, repeated at least 40 times on Windows and Linux, to measure the `PROTOCOL_VIOLATION` rate. The second measures how often stock HttpClient draws a 429 from consumer `/reg`. The third checks the HTTP/3 framing against the oracle fixtures.

## Conclusion

WARP has moved its trust anchor from keys inside packets to an identity inside TLS. Under WireGuard, the hard engineering is Noise crypto, a 3-byte tag and a userspace TCP/IP stack, which are the parts .NET handles worst. Under MASQUE L4, it is a few HTTP/3 frames and a pinned mTLS handshake, which are the parts .NET handles best. Cloudflare made this shift for FIPS compliance and HTTPS camouflage, not for third-party clients. It still turns a heavy port into a small HTTP/3 layer on System.Net.Quic. What remains fragile is a set of server-side constants Cloudflare can change unilaterally: the registration fingerprint, 20-byte connection IDs, exact-SNI checking in L4 and a possible PQC-only switch. WarpClient should therefore keep endpoints, SNIs, version strings and keys in configuration, not code. A WireGuard connector is worth keeping as a hedge, because that path depends on neither QUIC nor TLS fingerprints.

L4 also changes what a TCP connection is. In L3 modes the TCP session runs end to end from the local stack, so it could outlive a tunnel reconnect, although Cloudflare's egress NAT behaviour across reconnects is undocumented. In L4 the flow terminates at Cloudflare's edge and lives inside a single QUIC stream, so every idle reclaim, network change or `PROTOCOL_VIOLATION` resets every open `Stream` together. L4 also carries no UDP. Callers of `ITcpConnector` should treat connections as non-resumable and expect correlated bursts of resets. Workloads that need survivable long-lived flows or UDP bring the L3 path, and its missing .NET netstack, back onto the roadmap.
